# 根 Root · 手机摄影辅助工具

> 从照片读回光线，翻译成拍摄动作。

**一张普通模式拍下的照片 → 分析现场光线 → 给出专业模式的拍摄参数 → 拍完一键出片，同时输出 Lightroom 参数供 RAW 精修。**

纯前端单文件实现：零依赖、零后端、零 CDN，双击即用，照片全程在本机处理、不上传服务器。

## 一、为什么做这个

手机摄影有一组矛盾：

- **普通模式**随手一拍就有可用的照片，但画质被压缩；
- **专业模式**能拍出更好的画质，却要求使用者自己判断现场光线，给出 ISO、快门、曝光补偿、白平衡、对焦模式。

参数判断依赖经验。新手打开专业模式，往往只能乱拨滑块。

**根 Root 把这套判断自动化**：用一张普通模式照片当作测光表，把现场光线量化成数字，再按拍摄意图翻译成一组可以直接照着拨的参数。拍完之后，同一套分析结论继续用于后期——一键出片，并给出一份 Lightroom 参数清单，供 PC 端精修 RAW。

目标用户是 vivo 手机用户与摄影爱好者；因为参数逻辑与品牌无关，任何支持专业/手动模式的手机都能用。

## 二、核心功能

### 1. 光线分析（理解现场）

上传一张照片，立刻得到：

| 指标 | 含义 |
|---|---|
| 平均亮度 L（0–255） | 整张照片有多亮，是全部参数计算的基准 |
| 亮度直方图（256 级） | 阴影/高光有没有丢，并翻译成可执行的结论 |
| 平均 R / G / B | 偏色方向 |
| 估算色温（K） | 现场偏暖还是偏冷 |
| 标准差 stdDev | 对比度高低 |
| 饱和度 | 色彩浓度 |

直方图不是画着好看：它直接给出人话结论，例如"暗部丢失（左端堆积），建议适当 +EV 或放慢快门"。

### 2. 场景预设与动态参数

四个内置预设，各自对应真实的拍摄意图：

| 预设 | 意图 | EV 方向 | 测光 / 对焦 |
|---|---|---|---|
| 逆光 | 主体背光偏暗，提亮防止"黑脸" | 正向 | 点测光 · 中央重点 |
| 剪影 | 故意让主体欠曝成轮廓，保住亮背景 | 负向 | 点测光 · 高光 |
| 暗环境 | 照度低，提亮同时控噪 | 轻微正向 | 自动 / 手动，允许升 ISO |
| 高亮 | 强光 / 雪景 / 沙滩，防过曝 | 负向 | 点测光 · 高光，ISO 压到最低 |

**关键点：所有参数随照片动态计算，没有一个是写死的。** 同一个"逆光"预设，对着不同亮度的照片给出的 EV、ISO、快门、白平衡都不同（计算规则见第四节）。

### 3. 自定义预设

上传一张参考图，提取它的光线风格并保存为预设，之后可复用、改名、删除。选中自定义预设时，工具以"拍出接近参考图的效果"为目标给出参数；后期也用差值法把当前照片往参考图靠。

### 4. 一键出片 + Lightroom 参数

- **两个独立槽位**：上方「光线参考照片」负责测光与拍摄参数，会一直保留；「后期与导出」里的「专业模式拍的成片」负责后期与 Lightroom 导出。两者互不覆盖，方便按同一组参数反复重拍、逐个比较。
- **后期强度滑块（默认 30%）**：0% 输出原图（数学上逐像素一致），100% 为预设的完整效果。拖动实时重算。
- **Lightroom 参数清单**：曝光度、对比度、高光、阴影、白色色阶、黑色色阶、色温、色调、饱和度、噪点消除，供 PC 端 RAW 精修直接照抄。

**RAW 的定位**：专业模式可以同时拍 RAW + JPEG，本工具只处理 JPEG，RAW 留给 Lightroom——网页端不做 RAW 解码，这是刻意取舍，不是能力缺口。

### 5. 全程本地

零依赖、零后端、零 CDN，单个 HTML 文件双击即用，断网可用。**照片不上传任何服务器，也不写入任何远程存储。**

## 三、怎么用

**拍前（获取参数）**

1. 用普通模式随手拍一张现场照片，放到「1 光线参考照片」槽；
2. 读分析结果（亮度、直方图解读、估算色温），在「预设与参数」页选择拍摄意图；
3. 看着「2 专业模式建议参数」的参数卡——EV 是大字号主卡，ISO / 快门 / 白平衡 / 对焦四张小卡并列——在手机专业模式里拨到对应数值拍摄。

**拍后（出片与精修）**

4. 切到「后期与导出」页，把刚拍的成片放到「3 专业模式拍的成片」槽（上传后直接大图预览）；
5. 点"一键优化"，力度不合适就拖"后期强度"滑块，满意则"暂存"，最后一起保存（APK 内直接存入系统相册 `Pictures/Root/`）；
6. 需要极限画质时，按"Lightroom 参数"清单在 PC 端精修 RAW。

### 三种使用方式

- **安卓**：安装 `apk/根Root-摄影辅助工具.apk`（需允许"未知来源"安装）；
- **手机/电脑浏览器**：直接打开 `index.html`；
- **部署**：把 `index.html` 放到任意静态服务器或 GitHub Pages 即可。

自定义预设保存在本机（`localStorage` 存风格数值 + `IndexedDB` 存参考图原图），换设备不同步。

## 四、算法说明

### 1. 图像分析

先缩到最长边 200 像素再读像素（约 1/450 的数据量，速度提升明显，结论几乎不变），亮度用 Rec.709 感知亮度：

```
L = 0.2126·R + 0.7152·G + 0.0722·B
```

**为什么绿色权重最大（71.52%）**：人眼对绿光最敏感、对蓝光最迟钝。这是国际标准 Rec.709 的权重，与显示器、视频编码同源——把"看起来有多亮"变成可计算的数字。

同时统计平均 R/G/B、标准差、饱和度、256 级直方图，以及最暗端（<15）与最亮端（>240）的像素占比，用于直方图解读。

色温为工程近似：

```
色温 ≈ clamp(5500 - (平均R - 平均B)/255 × 4000, 2000, 10000)
```

红多偏暖、蓝多偏冷，用红蓝差值当尺子。**误差约 ±1000K**——它服务的目标不是精确白平衡，而是回答"现场偏冷还是偏暖"，这个精度足够。

### 2. 动态拍摄参数

核心只有一个量：**当前亮度与目标亮度的差距**。

```
dEv      = (L - effTarget) / 25          // 25 级亮度 ≈ 1 EV，除以 25 把亮度差换算成曝光档位
快门      = SHUTTER_LIST[clamp(baseShutterIndex - round(dEv), 0, 14)]
EV       = evOffset - dEv × 0.5          // 预设定向值给方向，差距做微调
ISO      = baseISO 按 isoMode 与现场亮度微调（有上下限保护）
白平衡    = 现场色温 × 0.6 + 预设目标色温 × 0.4
对焦模式   = |L - effTarget| > 30 ? 点测光/中央重点 : 自动
```

**ISO 为什么按 isoMode 分三种策略**：剪影与高亮的语义是"故意欠曝 / 防过曝"，**绝不能被一张暗照片把 ISO 拉高**——否则为了控噪而提亮，剪影就不成剪影了。所以 ISO 不是统一公式，而是按"意图"分流。

**目标亮度为什么不写死**：

```
effTarget = 预设目标 × 0.7 + 照片亮度 × 0.3
```

最初目标是固定值（逆光固定 150），结果是任何照片都被推向同一个亮度——一张 L=64 的宿舍照会被硬推到 150，画面发灰、高光压成一片白。改为加权后，同一张照片的有效目标是 124：提亮仍然明显，但不过冲；而且**照片越亮、干预越少**，明暗不同的照片不会被拉平。

### 3. 自定义预设（差值法，不套死值）

```
拍摄：dEv = (当前 L - 参考图 L) / 25，其余同上
后期：brightness = clamp(参考图 L - 当前 L, -80, 80)
      contrast   = (参考图 stdDev - 当前 stdDev) × 10
      saturation = (参考图饱和度 - 当前饱和度) × 100
      色温       = 按 R/B 通道比例修正
```

思路是"你离参考图差多少，就补多少"，而不是套一组固定数字。

### 4. 后期处理

一键优化的参数由两层相加，两层都乘"后期强度"：

```
后期参数   = ( 预设风格层 + 场景补偿层 ) × 后期强度
场景补偿层 = clamp(round((effTarget - L) × 0.6), -60, 60)
```

- **预设风格层**：预设固有的调色倾向（提亮 25 度、压一点对比等）；
- **场景补偿层**：随照片变化的动态部分——这才是需要按照片调整的力度。

**强度 0% 时所有系数归零，输出与原图逐像素一致。** 实测三张不同亮度的照片（逆光预设）：

| 测试图 | 原图 L | 强度 0% | 强度 30% | 强度 100% |
|---|---|---|---|---|
| 暗 | 52.2 | **52.2** | 71.2 | 118.3 |
| 中 | 120.4 | **120.4** | 131.6 | 156.8 |
| 亮 | 166.4 | **166.4** | 169.7 | 176.0 |

对比度与饱和度同样按强度线性缩放（系数 = `(1-k) + k×原系数`），所以 0% 是真正的"原图"。

`applyPost` 对每个像素依次执行：色温（R/B 通道系数）→ 亮度加值 → 对比度（标准 S 曲线因子 `(259(c+255))/(255(259-c))`）→ 饱和度 → 每步 clamp 到 0–255。顺序与修图师的常规流程一致。

分析用 200px 小图保证速度，后期用最大边 3000px 保证出片画质，两者共用同一套统计函数。

### 5. Lightroom 参数

```
色温   = 预设目标 × 0.7 + 现场实测 × 0.3
对比度 = 预设值 + (45 - stdDev) × 0.5
阴影   = 预设值 + (effTarget - L) × 0.5
曝光度 = 预设值 + (effTarget - L) / 50
```

共同思路：照片离目标越远，补正越大；越接近，越贴近预设基准。

### 6. 直方图绘制

256 个亮度级各计一个数，柱高用 **√ 归一化**后再缩放。这不是美化，是修正——按最大值直接缩放时，分布均匀的照片每级只有几个像素，柱子只有两三像素高、还是抗锯齿的淡色，等于没画。开方压缩动态范围后，暗部尖峰与中调细节都能看清。

## 五、实现中遇到的问题与解决

这一节是项目里真正的技术内容，每条都是实际动手时撞上的。

**1. 参数"看着动态，其实是死的"**
最初每个预设的 EV/ISO/白平衡都是固定值。测试同一个预设对着亮度 40 和亮度 200 的照片，给出的参数完全一样，等于没分析。改为先算出光照偏差 `dEv`，所有参数再由它推导；预设只提供"意图方向"（evOffset、目标亮度），不提供死值。

**2. 色温被现场值覆盖**
后期色温原本直接取现场估算色温，导致自定义预设的色温风格被冲掉（参考图是暖调、现场是冷光，结果给出冷调）。改成加权融合：预设目标 0.7 + 现场实测 0.3。

**3. 手机浏览器存不下参考图**
自定义预设最初把参考图转成 dataURL 存 `localStorage`，几百 KB 的图到第三张就报 `QuotaExceededError`。改为三层存储：`localStorage` 只存 8 个数值字段 + 降级缩略图；参考图原图以 Blob 存进 `IndexedDB`；本次会话展示用 `ObjectURL`。删除预设时三处同步清理（元数据 + IndexedDB 原图 + revoke ObjectURL）。`IndexedDB` 不可用（隐私模式等）时自动降级到缩略图方案，功能不中断。

**4. 保存预设卡住按钮**
早期版本读参考图时对原图做全尺寸解码再统计，手机上一张 5000×4000 的照片要等数秒，用户以为卡死会连点。改为 `createImageBitmap(file, {resizeWidth: 240})` 让浏览器在解码阶段就缩放，统计只用 240px 小图（毫秒级），原图仅做存储。并加了防双击 + 20 秒解冻兜底。

**5. 直方图解读要说人话**
只画直方图用户看不懂。加了文字结论层：高光像素 >5% → 建议降 EV；暗部 >5% → 建议提 EV；stdDev >70 → 高对比；<25 → 低对比。阈值是先验经验值，需真机继续校准。

**6. 真机上"保存"弹出的是分享面板，里面没有"保存到相册"**
第一次把 APK 装到手机上点导出，弹出的是系统分享面板，选项全是"发给别人"，**没有保存到本机**。根因是文件位置：`Filesystem.writeFile({ directory: Directory.Cache })` 把成片写在应用私有缓存目录，再通过 FileProvider 交给分享面板——相册应用不接受这种临时文件，系统自然不会给出"保存到相册"这个目标。Capacitor 官方 Filesystem 插件也补不了：`Directory.ExternalStorage` 只在 Android 9 及更早可用，`Directory.Documents` 在 Android 11+ 只能访问本应用创建的文件。
正解是走 MediaStore：引入 `@capacitor-community/media`，它把文件写进 `Pictures` 下本应用的相册目录并调用 `scanPhoto()` 登记，相册立刻可见，**且保存到自己的相册不需要任何存储权限**。实现时读插件 Java 源码避开了两个坑：`albumIdentifier` 在原生侧是**必填**（缺了直接 reject，不是可选项）；`blob:` 协议原生端读不到，必须转成 data URL。
顺带修掉一个隐藏 bug：`bridge.js` 作为入口脚本在 `<head>` 执行时 `body` 还没解析，`getElementById('download-btn')` 拿到 `undefined`，改文案的代码从未生效——改成 `DOMContentLoaded` 之后执行。同时发现网页层从来没有调用过桥接函数（桥接代码是死代码），补上了 `window.__nativeSave` 的调用与失败回落。

**7. 后期会过冲：暗照片被"提亮到发灰"**
原公式里"预设风格"和"场景补偿"直接相加。一张 L=64 的照片选逆光，补偿层算出 +52，加上风格层 +25，最终亮度加值 +77，整幅被抬到 139、高光压成一片白，画面发灰、层次丢失。两步修正：目标亮度向照片靠拢（见第四节），以及把强度滑块改为缩放全部后期参数——用户可自行在"原图"与"完整效果"之间取舍。

**8. 探针脚本把"柔和效果"做成了半透明叠色**
中间版本用半透明金色（`#efbb6024` 之类）做点缀，叠在深底上会被底色污染成脏灰，且整页其实是同一种颜色换透明度，观感单调。改为**实色色相分层**：底偏冷的灰蓝 → 面板 → 卡片 → 金色点缀，每级用实色，不靠透明度叠加。

**9. 界面可读性：浅色版对比度不达标（已弃用该版本，但结论保留）**
试做过浅色版，用 WCAG 对比度逐项校验时发现两个真问题：主参数数值用亮金 `#cf9130` 在白底上只有 **2.57:1**（几乎看不清），次要文字 3.51:1。原因是浅色下暖色系点缀必须压深才有效。最终交付保留暗色版，但这条经验留下了：**配色不是看着顺眼，是要量出来的**——暗色版同样逐项校验过（最低 6.08:1，全部达 AA）。

## 六、技术要点

全部能力来自浏览器标准 API，**运行时零第三方依赖**：

- **像素计算**：Canvas 2D `getImageData` / `putImageData`，逐像素做亮度统计与后期；
- **智能缩放**：分析用最长边 200px 小图，后期用最长边 3000px，共用同一套统计函数；
- **存储三层**：`localStorage`（数值）+ `IndexedDB`（Blob 原图）+ `ObjectURL`（会话内展示）；
- **性能与稳定性**：`createImageBitmap` 解码期缩放、`willReadFrequently: true` 避免画布回读惩罚、异步按钮防卡死、`IndexedDB` 不可用时自动降级、`resolveObjectURL` 及时释放；
- **界面**：全部样式收敛为 28 个设计变量，JS 只依赖元素 id 与 `.hidden` 类——样式与逻辑解耦，重做视觉不动算法；
- **打包**：Vite 相对路径构建（`file://` 与 WebView 通用）+ Capacitor 安卓壳；`src/bridge.js` 作为独立入口打进产物。

## 七、已知边界

诚实写清工具的能力范围：

- 参数是**起手参数**，不是精确测光表。真实拍摄受镜头、测光模式、机内算法影响，建议拍一张回放确认后微调；
- 色温为工程估算，**误差约 ±1000K**，只适合判断冷暖倾向；
- 只处理 JPEG，网页端不解码 RAW（RAW 交给 Lightroom）；
- 光线分析为**全局平均 + 直方图**，不做局部点选测光。逆光时若背景极亮、主体极暗，全局平均值会高估现场亮度——此时应以预设意图（提亮主体）为主，本工具已按此设计参数方向；
- **剪影预设**在本身偏暗的照片上会压暗较多像素（实测约 26% 落入纯黑）。这是"减少裁剪"护栏尚未加入的已知点；
- 一次处理一张照片，不做批量；
- 直方图解读阈值、ISO 上下限为经验值，需真机继续校准；
- 自定义预设存在本机，不跨设备同步、无云端；
- 安卓"保存到相册"依赖 `@capacitor-community/media`，**已在真机验证过流程，但不同厂商 ROM 的相册扫描行为可能略有差异**。

```
root-photo-assistant/
├── index.html                 # 全部界面 + 算法（单文件，双击即用，无需构建）
```

## 九、后续方向（按优先级）

1. **给剪影预设加"减少裁剪"护栏**：限制压暗导致纯黑的像素比例，避免主体糊成一块；
2. `下载全部` 改为 zip 单包下载，绕开部分手机浏览器对多文件下载的拦截；
3. **空间分析识别真实逆光**：目前用全局平均亮度，原理上分不清"主体暗"与"整体暗"；可通过分区统计辅助判断（但需先解决"主体在哪"的问题，否则可能猜错）；
4. 读取 EXIF（ISO / 快门 / 光圈）校准估算值，给出更贴近的起手参数；
5. 色温改用灰点白平衡 + CCT 查表，把 ±1000K 压到 ±200K 量级；
6. **成片反推闭环**：保存"参考照片 → 建议参数 → 实际成片"的配对数据，用成片效果反推校准预设。

## 十、AI 工具使用说明与来源标注

按实验室要求，如实说明本项目对 AI 工具的使用与第三方来源。

**使用的 AI 工具**：DeepSeek Harness（DSH）配合 Claude / DeepSeek 模型，用于代码编写、重构、界面调整与问题诊断。

**AI 协助的部分**：
- 界面样式与布局的重写（多轮配色/层级调整）；
- 部分算法的实现与重构（参数计算函数的拆分、后期强度滑块）；
- 大量诊断脚本（用 Node 复刻算法跑真图，量化验证结论）；
- 本文档的技术表述整理。

**由本人完成的部分**：
- 项目定位、需求确定与全部功能取舍；
- 真机安装、拍摄测试与效果判断（AI 无法拍照片，所有真机结论都来自实拍验证）；
- 对 AI 产出的核对与验收：例如用三张不同亮度的照片实测"强度 0% 是否等于原图"、用 WCAG 公式逐项核对配色对比度、在真机上确认相册保存流程；
- 提出并驱动了多个关键修正方向（如"暗照片被提亮到发灰"、"分享面板里没有保存到相册"）。

**第三方依赖与许可**：
- [Capacitor](https://capacitorjs.com/)（MIT）——安卓壳与原生桥接；
- [Vite](https://vitejs.dev/)（MIT）——构建工具；
- [`@capacitor-community/media`](https://github.com/capacitor-community/media)（MIT）——写入系统相册；
- `@capacitor/filesystem`、`@capacitor/share`（MIT）——早期导出方案，保留兼容；
